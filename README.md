# Human-AI Investigation Lab

A small tool that helps a human investigator look into a security case. It ranks evidence two different ways (simple rules, and a small ML model), builds a timeline, draws a graph of how people/devices/IPs are connected, and compares a few possible explanations for what happened.

The AI never makes the final call. It only shows evidence and suggestions. Only a human investigator can record the final decision, and that decision goes into a log that can't be quietly edited later.

Built with Python + Flask on the backend, scikit-learn for the ML part, and React + Vite on the frontend.

## What it does

- **Evidence ranking (two ways):** simple rules, and a small ML model. Both explain why an event got its score, not just the number.
- **Timeline:** puts all events for a case in order and flags anything odd, like the same user logging in from two places at once.
- **Event relation graph:** a graph view showing which users, devices, IPs, destinations, and processes are connected because they showed up in the same event. Thicker lines mean more shared events. It's laid out as a plain circle instead of a "smart" auto-layout, so the same case always looks the same every time you open it.
- **Hypotheses:** compares a few possible explanations (like "credential compromise" vs "legit admin work") and shows the evidence for and against each. If the evidence is too weak or too close to call, it says so instead of guessing.
- **Robustness checks:** tests what happens to the results if some evidence is missing, duplicated, delayed, or noisy, so you can see how stable the conclusions really are.
- **Audit log with tamper detection:** every decision a human records is saved permanently, and each entry is linked to the one before it with a hash. If anyone edits, deletes, or reorders an old entry, the app can tell and points at exactly which entry is broken.
- **Upload your own data:** bring a CSV of your own events and it runs through the exact same ranking/timeline/hypotheses/graph as the built-in demo cases. See "Uploading your own data" below.

## What each file does

**Backend (`backend/`)**

- `app.py` — the Flask server. Every API route lives here; it just calls into the files below and returns JSON.
- `config.py` — every setting (thresholds, seeds, ports) in one place, instead of scattered across files.
- `data_loader.py` — reads the CSV files in `data/` and turns each row into a plain dictionary.
- `make_dataset.py` — builds the demo dataset: 4 made-up cases plus 3 real cases (see below).
- `uploads.py` — lets someone upload their own CSV instead of using a demo case. Kept in memory only, nothing is written to disk.
- `case_generator.py` — builds a much bigger (160-case) made-up dataset, used only for the evaluation, not shown in the UI.
- `baseline.py` — the rule-based scorer. No machine learning, just plain if-checks with a reason attached to each one.
- `ml_ranker.py` — the ML scorer (logistic regression). Trains on every case except the one it's scoring, so it's never tested on data it already saw. Also explains its own scores, feature by feature.
- `hypotheses.py` — compares the possible explanations for a case using keyword matching, with basic handling for negation ("not associated with malware" shouldn't count as evidence).
- `hypothesis_classifier.py` — a learned (not keyword-based) version of the same comparison, kept separate and marked experimental.
- `timeline.py` — sorts events by time and flags timestamp conflicts.
- `event_graph.py` — builds the relation graph (which entities showed up in the same event).
- `robustness.py` — deliberately damages a case's evidence (removes some, duplicates some, delays it, adds noise) and checks if the conclusion changes.
- `evaluation.py` — the actual evaluation code: train/test splitting, confidence intervals, calibration, which features matter.
- `run_experiments.py` — runs everything in `evaluation.py` on the 160-case dataset and writes a report.
- `audit_log.py` — saves every investigator decision, permanently, with the hash chaining described above.

**Frontend (`frontend/src/`)**

- `App.jsx` — holds the app's state and switches between tabs.
- `api.js` — every network call to the backend, in one place.
- `components/` — one file per tab/section (evidence, timeline + graph, hypotheses, robustness, decision form, sidebar).

**Everything else**

- `tests/` — the test suite, one file per backend module.
- `data/` — the CSV files that get generated by `make_dataset.py` and `case_generator.py`.
- `results/` — where the audit log and the evaluation report get written.

## Demo cases

Four are made up, three are real:

| Case | What happens | Ground truth |
|---|---|---|
| CASE001 | Midnight login from a foreign IP, then contact with a malware domain | credential_compromise |
| CASE002 | Same kind of midnight login, but there's an approved maintenance ticket | legitimate_admin_activity |
| CASE003 | Large data transfer to personal cloud storage right after someone resigned | insider_data_exfiltration |
| CASE004 | Vague early-morning activity that doesn't clearly match anything | insufficient_evidence |
| CASE005 | The real 2013 Target Corporation data breach | credential_compromise |
| CASE006 | The real 2016 Uber data breach | credential_compromise |
| CASE007 | The real Levandowski / Waymo trade secret theft case | insider_data_exfiltration |

## Testing it against a real case, not just made-up ones

CASE005 isn't a template — it's built from the actual public record of the 2013 Target breach: the U.S. Senate Commerce Committee's "Kill Chain" analysis and Target/DOJ's own public statements. Real dates, real named vendor (Fazio Mechanical Services, the HVAC contractor whose stolen credentials got the attackers in), real sequence of events (vendor credential theft → POS malware → an ignored antivirus alert → exfiltration over FTP). The only placeholders are the exact time of day and internal IPs/hostnames, since those were never made public.

Running the actual system against it:

- **Hypotheses engine got it right.** It correctly landed on `credential_compromise` with a clear score (5 vs 0 for the other two), matching the real cause. The keyword matching ("malware", "malicious") picked up naturally from real report language — I didn't have to write the events to contain magic words.
- **The ML ranker also did well.** Trained only on the 4 made-up cases and tested on this real one, it correctly ranked the actual exfiltration event (data leaving over FTP) as the most suspicious event in the case.
- **The rule-based baseline showed a real weakness.** Its "known-bad destination" rule only fires if the destination name literally contains the word "malicious" or "c2" — which is true of the made-up dataset (domains are literally named things like `malicious-c2.example`) but not of a real destination name like `external-ftp-server`. Same for its "unrecognized IP" rule, which only checks non-blank IPs — when the real IP simply isn't public record, that check silently does nothing. This is a fair, honest gap: the rules were tuned to how the synthetic dataset happens to be written, not to real-world naming.
- **Timeline, event graph, and robustness checks all ran cleanly** on the real case with no special-casing needed.

Sources for CASE005, CASE006, and CASE007 are cited in `data/cases.csv`'s notes column for each row.

CASE006 is built from Uber's own November 2017 public disclosure of its 2016 breach (attackers used credentials stolen from a private GitHub repo to reach an AWS account holding rider/driver data), and CASE007 from Waymo's 2017 lawsuit and the DOJ's 2019 indictment of Anthony Levandowski for taking self-driving car trade secrets to a competitor.

Running the system against these two turned up a real, honest limitation:

- **The hypotheses engine abstained on both** (`insufficient_evidence`), instead of landing on the correct answer. The reason is exactly what you'd expect from keyword matching: real incident reports use words like "unauthorized access to a private repository" or "downloaded confidential files," not the handful of keywords the matching was written against. It worked on CASE005 mostly because Senate report language happened to use words like "malware" directly.
- **The ML ranker still did its job.** Because it scores events on structured features (odd hour, known/unknown IP, risky process, severity) rather than matching words in a description, it kept correctly ranking the actual attacker/exfiltration events highest in both cases, even though it never saw either case during training.

So the honest summary across all three real cases: feature-based scoring (the ML ranker) generalized to real-world data; keyword-based scoring (the hypotheses engine) generalized once out of three tries. That's a genuine gap, not a talking point — it's exactly the kind of thing a human investigator needs to know before trusting either tool.

## Uploading your own data

Instead of picking one of the demo cases, you can upload a CSV of your own events from the sidebar. It's treated as a new case and goes through the exact same scoring, timeline, hypotheses, and graph code as everything else — nothing special-cased for it.

The file needs a header row with these columns: `timestamp, event_type, user, device, source_ip, destination, process, severity, source, description`. Two columns are optional:

- `event_id` — if it's missing, one is generated for you.
- `label` — if it's missing, events are stored as `unlabeled`, which is completely fine. The ML ranker only needs labels for the cases it *trains on* (the built-in demo cases), not for the case it's actually scoring — your own data is exactly the kind of thing it's meant to be pointed at without already knowing the answer.

A few things worth knowing:

- Uploaded files are kept in memory only, for as long as the server keeps running. Nothing is written to `data/` or saved anywhere.
- There's a 2,000-row limit per upload, just so one huge file can't hang the ML ranker or the relation graph.
- An uploaded case has no ground truth to check against, so the hypotheses/ML results are shown as-is — there's no "correct answer" column for the app to grade itself against, the same as it would be for a real investigation.

## Known limitations

- The 4 made-up demo cases, and the larger 160-case dataset used for evaluation, are still templated. Only CASE005, CASE006, and CASE007 are grounded in real incidents.
- The hypothesis matching is just keyword matching with basic negation handling, not real language understanding. It worked on CASE005 but abstained on both CASE006 and CASE007 — see above. Three real cases is a small sample, but two out of three abstaining is a real signal, not noise.
- The baseline's rules are tuned to how the synthetic data is written (see above) — real infrastructure won't always look like that.
- There's no completed human study yet, just the plumbing needed to run one someday (study groups, timing, an error-injection mode for testing over-trust in AI).
- The confidence numbers and stats from `run_experiments.py` only really mean something on the 160-case dataset, not the small demo set.
- Uploaded data isn't persisted, so if the server restarts, any case you uploaded is gone — you'd need to upload it again.
